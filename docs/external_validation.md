# External validation — do the detectors generalize beyond synthetic data?

**Date:** 2026-07-16 · **Harnesses:**
[`training/validate_sentinel_ait.py`](../training/validate_sentinel_ait.py),
[`training/validate_cassandra_cert.py`](../training/validate_cassandra_cert.py)

## Why this exists

SENTINEL and CASSANDRA are trained and tuned on the synthetic LTI traffic
generator. SENTINEL's situation is circular by construction: its training
labels come from the same rule engine (`app.rules.window_rule_level`) that also
gates inference, over log lines cloned from the generator — so its reported
`holdout_accuracy: 1.0` measures self-consistency, not real-world skill. This
pass feeds **independently generated public datasets with real ground truth**
through the **unmodified** detection code to see what actually transfers.

**The production models were NOT retrained or retuned.** These datasets are a
different problem domain; using them as training data would be the very mistake
this exercise exists to expose. Every number below comes from the shipped
artifacts. The two ablation/analysis runs monkey-patch a rule *in the harness
process only* and restore it immediately — the committed code is untouched.

## Track A — SENTINEL vs AIT Log Data Set v1.1

**Dataset.** [AIT-LDS v1.1](https://zenodo.org/records/4264796) (Landauer et al.,
AIT Austrian Institute of Technology; CC-BY-NC-SA 4.0). Four independent
mail-server testbeds (Horde webmail on Apache/PHP), six days of simulated user
traffic, multi-stage attacks on day five: nmap/nikto scanning, SMTP enumeration,
Hydra brute-forcing the login, a webshell planted via curl, and post-exploitation
commands. Ships Apache access logs **plus per-line label files** — genuinely
independent ground truth, generated by a different team for a different stack.

**Method.** Each Apache line is reshaped into SENTINEL's gateway envelope
(`services/sentinel/app/logparse.py`), preserving the request path verbatim
(the path is where SENTINEL's signatures live), and fed through the real
`Pipeline(Settings(), SentinelModel.load(...))`. SENTINEL scores
`(client_ip, 1-minute)` windows, so per-line labels are aggregated: a window is
attack-ground-truth if it contains ≥1 attack line, and predicted-attack if the
pipeline emits a `log_classification` alert. Pooled over all four testbeds:
50,945 windows, 172 of them attack, 27,501 attack lines.

**Results.**

| Configuration | precision | recall | F1 | benign FP rate |
|---|---|---|---|---|
| As-shipped | 0.004 | **0.849** | 0.007 | 0.804 |
| Stack-agnostic signatures only (ablation) | 0.171 | 0.192 | 0.181 | **0.003** |

Per-attack-class window recall, as-shipped: nikto scanning **91%** (61/67),
webshell commands 85% (46/54), webshell upload 100% (6/6), Hydra brute-force 74%
(32/43), SMTP VRFY enumeration 100% (4/4).

**What this means (the honest reading).** Two facts sit together:

1. **SENTINEL detects the attacks** — 85% window recall against a dataset it has
   never seen, generated by a different team for a different application. The
   detection *approach* — rule pre-filter over request paths + windowed model —
   fires on independently-authored nikto/Hydra/webshell activity.
2. **As-shipped precision on this domain is meaningless (0.4%)**, and for a
   specific, understood reason: SENTINEL's scanner rule treats any `.php` path as
   a probe. That is correct for the non-PHP LTI stack it defends — there, any
   `.php` request *is* anomalous — but AIT's target is a PHP webmail app where
   80% of *benign* traffic is `.php`. So the same rule that catches the attacks
   also flags most benign windows: on a PHP application, a path-based rule cannot
   separate benign PHP traffic from PHP-targeting attacks.

The ablation isolates that entanglement. Disabling **only** the `.php`-means-probe
clause (keeping the stack-agnostic signatures: `../` traversal, SQL
metacharacters, dotfiles, `/wp-`, `/actuator`) drops the benign false-positive
rate from 80.4% to **0.3%** — and still catches **49% of nikto** on a foreign
application, because nikto's dotfile and traversal probes are intrinsically
malicious regardless of stack. The app-specific detection (Hydra on `login.php`,
webshell over `.php`) falls to zero, confirming it was riding on the stack
assumption.

**Conclusion.** SENTINEL's *portable signature layer* — the rules that match
intrinsically malicious request shapes (`../`, SQL metacharacters, sensitive-file
probes) — genuinely generalizes: it flags independently-generated path-based
attacks at a 0.3% false-positive rate on an application it was never built for.
SENTINEL's *application-tuned layer* — the `.php` heuristic and the XGBoost model
trained on LTI log families — does **not** transfer to a foreign application, and
should not be expected to. This is exactly why the production model stays trained
on LTI traffic and is never retrained on foreign data: SENTINEL is an
application-specific log classifier for the LTI gateway, not a general-purpose web
IDS, and this validation makes that boundary concrete instead of leaving it
implicit behind a self-referential 1.0 accuracy.

## Track B — CASSANDRA vs CERT r4.2 insider-threat dataset

**Status: harness built and self-tested; run pending the dataset download**
([CERT r4.2](https://kilthub.cmu.edu/articles/dataset/Insider_Threat_Test_Dataset/12841247),
~1 GB, manual browser download — KiltHub blocks scripted fetches). Results will
be appended here when the data is in place.

**Dataset & method.** CERT r4.2 is 1000 users over 17 months, 70 of them
malicious, including a removable-media data-exfiltration scenario with per-user
ground truth (`answers/`). CASSANDRA watches per-entity *volume drift*; CERT has
no money, but the same signal exists as a user's daily count of data-movement
events (`file.csv` / `device.csv`). Per user, `validate_cassandra_cert.py` buckets
that count per day, uses file-content length as a winsorized size proxy for the
amount chart, and drives the shipped `PayerDrift.update()` exactly as
`services/cassandra/tests/offline_check.py` does. CUSUM on standardized
per-bucket z is bucket-duration-agnostic, so the shipped `Params` (warmup 30
buckets, k=0.75, h=6/10) apply at day granularity unchanged — this validates the
*shipped* detector, not a re-tuned one. The measurement mirrors offline_check's
fleet ARL soak: exfil-user detection rate and delay vs. a benign false-alarm
budget across the 930 normal users.

## Reproducing

SENTINEL harness needs `numpy`/`xgboost`/`drain3`, whose pinned versions lack
Python 3.14 wheels, so it runs in a throwaway 3.13 venv; the CASSANDRA harness is
stdlib-only on host 3.14. Datasets live under the gitignored `training/datasets/`.
See [training/README.md](../training/README.md) for the exact commands.
